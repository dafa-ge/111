# 技术设计

这份文档记录**参数为什么取这个值**。所有参数集中在 `app/rag/config.py`，改之前先读这里。

## 1. 切片

| 参数 | 值 | 理由 |
|---|---|---|
| `CHUNK_SIZE` | 512 | 制度文档一段通常 200~600 字，512 基本保证一段不跨块 |
| `CHUNK_OVERLAP` | 80 | 约 15%，防止"结论在上块、条件在下块"被切断 |
| `MIN_CHUNK_LEN` | 20 | 短的表格残留、页码行直接丢弃 |
| `SEPARATORS` | `\n\n \n 。；！？，、 ` | 中文必须把句末标点排在英文分隔符之后，否则长句会在句中硬切 |

切片是字符级而非 token 级：中文按 token 切容易在词中间断，检索时反而更难命中。

## 2. 检索

双路召回 + RRF 融合：

1. 向量召回 Top-8（余弦）；
2. BM25 召回 Top-8（jieba 分词，`rank_bm25`）；
3. RRF（`k=60`）合并排序，取 Top-4 进 prompt；
4. **邻接扩展**：命中的块带上同文件前后各 1 块，权重 0.85 参与排序。

RRF 而不是加权求和，是因为两路分数量纲完全不同（余弦 0~1、BM25 无上界），调权重等于调两个语料的分布，换语料就失效；RRF 只用名次，跨语料稳定。

邻接扩展的必要性：制度条款经常"标题块"和"内容块"被切开，只召回内容块会缺上下文。带相邻块的代价是 prompt 变长，所以只带 ±1 块、且降权。

## 3. 拒答

```
cos = 1 - distance
cos >= 0.60                      → 相关
0.45 <= cos < 0.60 且 bm25 >= 1  → 相关
其余                              → 拒答
```

为什么是双条件：单看余弦，短问题（"年假几天"）对长条款的分数天然偏低，会误拒；单看 BM25，同义改写（"休假额度" vs "年假天数"）会漏。两者都不满足才算"没找到"。

`0.45 / 0.60` 是在这个语料上用回归集扫出来的：0.60 以上几乎无误召，0.45 以下误召明显上升。换语料需要重扫（`python -m app.rag.eval --sweep`）。

## 4. 记忆

两条独立链路：

**短期**（`memory/short_memory.py`）：进程内 + 落盘，同一 session 保留最近 12 条消息（约 6 轮），文件 7 天清理。

**长期**（`memory/long_memory.py`）：只抽取五类事实（岗位/部门/称呼/常驻地点/明确偏好），存独立向量库，30 天过期，每条截断 100 字。

关键取舍：**记忆条数 ≤ 6 时全量注入，> 6 才走向量检索**（阈值 0.50）。

原因实测得出："我的住宿标准该按哪一档"对记忆"岗位：市场岗"的余弦只有 0.43，低于任何合理阈值——短事实句的向量区分度本来就差。条数少时全量注入既准又便宜；条数多时向量检索只为控制 prompt 长度。

注入的记忆在 prompt 里标注"非制度条款"，防止模型把它当制度依据引用（这点在护栏的后置校验里也有覆盖）。

LLM 兜底抽取默认关闭：qwen3:4b 做一次总结要 6~10 分钟，且会和前台问答抢 Ollama；规则抽取在这个场景够用。

## 5. 护栏

三级词表（`sensitive_words.txt`）：

- **HARD**：命中即拒答，不进检索；
- **SOFT**：命中后放行，但输出阶段触发模型复核；
- **白名单**：用于抵消误伤（如"离职证明怎么开"含"离职"但属正常业务）。

后置校验只在"问题本身命中 SOFT"时才调模型，不是每条都调——否则每条请求多花几分钟，没人会用。

## 6. 鉴权

JWT（HS256）+ 两级角色：

- 员工：提问、看自己的会话与记忆、查自己的资料；
- 管理员：上传/重入库/移出索引、看审计、看全部资料。

设计上的两个细节：

1. **JWT 密钥落盘**（`data/jwt_secret.key`，首次启动生成），不写死在代码里，重启后旧 token 仍有效；
2. **应急开关** `RAG_AUTH_ENABLED=0`，跳过鉴权按本机管理员放行——用于本机调试，默认开启。

账号与员工档案分开存：`users.json` 放登录凭据（pbkdf2 哈希），`user_info.json` 放业务档案（工龄、年假余额）。管理员不在员工档案里，避免"查到管理员年假"这种脏数据。

## 7. 向量后端为什么默认不是 Chroma

`chromadb==1.0.20` 在这台机器（Python 3.13 + Windows）写入时 Rust 内核段错误，进程直接挂。排查过版本、重建目录、换 collection 参数，都没解决。

所以做了双后端：

- `chroma`：标准接口，量大时用；
- `simple`：纯 numpy 余弦，数据全在内存，几十万向量以内够用。

`VECTOR_BACKEND=auto` 时读 `data/backend_decision.json`（首次建库时自检写入），避免每次启动重复试错。功能完全一致，只是不再依赖 Chroma 的 Rust 内核。

这个兜底不是"退而求其次"——对一个几千到几万切片的内部知识库，numpy 暴力检索的延迟完全可以接受，换来的是零原生依赖。

## 8. Agent 编排为什么不用 LangChain

四个理由：

1. **步数可控**：企业问答不需要无限推理，固定 8 步上限，超了直接返回"未能确定"，比无限循环好；
2. **可观测**：每一步的输入输出都进审计，出问题能追到具体一步；
3. **依赖轻**：少一层框架，`pip install` 快，Windows 上少一类兼容问题；
4. **工具权限**：工具函数里直接校验 `user.role`，框架层不用再搭一套权限。

代价是要自己写状态机（`app/agent/graph.py` 约 100 行），但换来的确定性对这个场景值得。

## 9. 模型参数

`qwen3:4b` 的坑：默认 thinking 会一直写到 token 用尽，导致没有结束标记，把整段思考当答案输出。所以：

- `num_ctx=8192`、`num_predict=4096`（给思考留足空间）；
- 用户消息尾部加 `/no_think`（`NO_THINK_TAG=True`）；
- 换非 qwen3 模型时把这一项关掉，否则会污染 prompt。
